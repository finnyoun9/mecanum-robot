## T1：让协议模拟器反映实测的被控对象（优先）

**现状问题**：`tools/stm32_uart_sim.py` 第 151-155 行直接把"命令轮速"当作"实际轮速"积分成编码计数——瞬间跟随、无死区、无上限、无惯性。这意味着 ROS 2 侧任何闭环测试都是在一个理想对象上做的，测不出真实系统会遇到的问题。

现在有实测数据了（见 [hardware-closed-loop-roadmap.md](hardware-closed-loop-roadmap.md) 的"占空比 → 转速实测曲线"）：

- 20% 占空比以上近似线性，斜率约 0.986 edges/(duty·s)
- **启动死区**：5% 占空比四轮完全不转，10% 正常。注意线性段外推交于 ~3%，但静摩擦让**启动**需要更大占空比——两者不是一回事
- 满占空比外推约 4.27 rev/s（≈ 0.81 m/s 车速上限）

**要做的**：给模拟器加一个更接近真实的对象模型，至少覆盖速度上限和死区；一阶惯性（时间常数）目前**没有实测数据**，如果要加，必须在代码注释里标明是估计值而非实测（参考 `mock_hal.c` 里 `max_wheel_rps` 的注释写法）。

**验收**：`tools/verify_sil.sh` 仍通过；下发超过 0.81 m/s 的 `/cmd_vel` 时里程计不再线性外推出物理上不可能的速度。

## T2：给标定常数加一道防线

**背景**：`EDGES_PER_WHEEL_REV` 曾按厂商典型值推导成 1496，实际实测是 224（1 倍频），**错了 6.7 倍**。这个常数在三处各自硬编码（固件 `encoder.h`、ROS 2 `mcr_hardware_interface.cpp`、模拟器 `stm32_uart_sim.py`），当时是靠人工发现并逐个改的。

> ⚠️ **2026-08-23 更新：该常数现为 448**——编码器改为 A 相双边沿解码（2 倍频）以提升速度分辨率。写测试时用 448，别用 224。这次改动同样要手工改三处，正好说明本任务的必要性。

**要做的**：让这类不一致能被自动发现，而不是靠下次有人想起来。具体方式你判断，可选方向：

- 给 `mcr_bringup` 加单元测试，断言"N 个编码计数 → 预期弧度/米"，用实测常数写死期望值。这样任何一处常数被改动而其他处没跟上，测试就会红
- 或者更彻底：把常数收敛到单一来源，其余处引用它

后者更好但跨语言（C / C++ / Python）不容易，别为此过度设计——**能让 CI 抓住不一致就达到目的了**。

**验收**：故意把某一处常数改错，CI 会失败。

## T3：标出 lx / ly 未实测

`mcr_hardware_interface.cpp` 第 18-19 行的 `LX_DEFAULT = 0.10`、`LY_DEFAULT = 0.12`（半轴距 / 半轮距）从项目建立起就是**估计值，从未实测**。麦克纳姆运动学里横移和旋转分量直接依赖这两个数，错了会导致里程计在横move和转向时系统性偏差——而前进方向看起来却是准的，很隐蔽。

**要做的**：不需要你测（要拿尺量真车，属于硬件侧）。只需要：

- 在代码注释和 [hardware-closed-loop-roadmap.md](hardware-closed-loop-roadmap.md) 的 M4 章节明确标注这两个值**未实测**，并写明测量方法（轴距 = 前后轮轴中心距，轮距 = 左右轮中心距，各取一半）
- 在 M4 验收条件里加上"用实测 lx/ly 替换默认值"

这条的价值是**防止它被默认成已验证**——和 6V 供电那次是同一类问题。
